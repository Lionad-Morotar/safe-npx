## Problem Statement

`npx -y pkg@latest` 会直接拉取最新版。如果该版本刚被供应链攻击（Supply Chain Attack），用户立刻中招。需要一个透明替代工具，在调用 npx 之前锁定到「上一个版本 + 至少发布 1 天」的安全版本。

## What Makes This Cool

一条命令替换。`snpx -y create-react-app@latest` 和 `npx -y create-react-app@latest` 体验完全一致，但自动跳过可能有风险的新版本。用户零学习成本。

## Constraints

1. PoC — 概念验证，不需要生产级打磨
2. 单文件实现，~250 行（含导出、测试支持、帮助文档）
3. 零外部依赖（Node 18+ 内置 fetch）
4. 本地 24 小时缓存，避免重复 registry 请求
5. 参数完全兼容 npx（透传）
6. 只拦截含 `@latest` 的调用，裸 `npx pkg` 直接透传（npx 会优先用本地版本，已足够安全）
7. snpx 自更新提示：`--self-update` 检查新版本，遵循同样策略（24h 安全窗口）；检测到新版时提示用户运行 `npm update -g @lionad/safe-npx`（不自 exec）。`--unsafe-self-update` 可绕过安全窗口。

## Premises

1. 查 npm registry 版本列表 + 发布时间，找 latest-1 且 >=1 天的版本 — AGREE
2. CLI 名 `snpx`，参数完全兼容 npx — AGREE
3. 解析后 exec `npx pkg@resolved_version ...rest_args` — AGREE
4. 找不到满足条件的版本 → 报错退出，不 fallback — AGREE
5. 本地缓存 24 小时（`~/.cache/snpx/{pkg}.json`）— AGREE（用户新增）

## Approaches Considered

### Approach A: 单文件 PoC (SELECTED)
- Summary: 单个 snpx.js，~150 行，零外部依赖
- Effort: S
- Risk: Low
- Pros: 快速验证概念，部署简单，`npm link` 即可用
- Cons: 测试需要 mock fetch，错误处理相对粗糙

### Approach B: 完整 TypeScript 项目
- Effort: M
- 未选择：PoC 阶段过度工程化

### Approach C: Shell 脚本
- Effort: S
- 未选择：错误处理差，测试困难

## Recommended Approach

**Approach A: 单文件 PoC**

```
snpx/
├── package.json        # bin: snpx -> snpx.js
├── snpx.js             # 全部逻辑 ~150行
├── test/
│   └── snpx.test.ts    # vitest
└── README.md
```

核心流程：
1. 解析 argv：找到匹配 `{@scope/}pkg{@range}` 的 token（range 含 `latest` 时触发解析，否则透传 npx）
2. 检查 `~/.cache/snpx/{pkg}.json`，未过期则用缓存版本
3. 缓存 miss → fetch `https://registry.npmjs.org/{pkg}`（注意：完整 manifest 可能很大，PoC 可接受）
4. **"latest-1" 算法**：从 registry `time` 对象按发布时间降序排列，找到 `latest` dist-tag 对应版本，取其前一个（时间更早的）版本。同时间戳时取较低 semver 作为 "前一个"
5. 检查该版本发布时间 >= 24h
6. `fs.mkdirSync(cacheDir, { recursive: true })` 创建缓存目录，写缓存
7. `child_process.spawn('npx', [pkg@resolved_version, ...rest], { stdio: 'inherit' })` — 用 spawn 而非 exec（exec 默认 1MB 缓冲上限，npx 安装大包时易截断；spawn 实时流式无上限，且支持 TTY 继承）
8. **注意**：snpx 不注册 SIGINT handler，让 Ctrl+C 信号自然传播给 npx 子进程

缓存格式：
```json
{"version":"1.2.3","resolvedAt":1712000000000}
```

## Open Questions

- 是否支持 scoped packages（如 `@vue/cli`）？→ PoC 阶段先支持
- npx 收到的是 `pkg@1.2.3` 而不是 `pkg@latest`，npx 会重新下载吗？→ 不会，npx 按精确版本缓存

## Success Criteria

1. `snpx -y cowsay@latest` 成功执行，使用 latest-1 版本
2. 24 小时内重复执行不触发 registry 请求
3. 所有 npx 参数透传且正常工作
4. vitest 测试覆盖：版本解析、缓存读写、时间过滤

## Distribution Plan

`npm link` 本地使用。如果 PoC 验证成功，后续可发布到 npm registry。

## What I noticed about how you think

- 你一开始就提到了「缓存机制」，说明你在意实际使用中的性能影响，而不是只做玩具。这种对真实场景的敏感度比很多 PoC 作者强。
- 你选了「透明替代」而不是「透明+解释」，说明你优先考虑零摩擦 adoption。好的工具不需要被注意到。
